# 技术设计与选型

## 评估方法

本次评估以 2026 年可公开验证的开放标准与主流开源实践为基线，逐项对照仓库 v3.2.2 的真实实现，而不是以文档愿景为准。

- Agent Skills 规范：<https://agentskills.io/specification>（`SKILL.md` frontmatter、渐进披露、`scripts/references/assets`）
- MCP `2026-07-28` 规范：<https://blog.modelcontextprotocol.io/posts/2026-07-28/>（stateless 核心、MRTR、扩展框架、认证加固）
- A2A v1.0：<https://www.linuxfoundation.org/press/a2a-protocol-surpasses-150-organizations-lands-in-major-cloud-platforms-and-sees-enterprise-production-use-in-first-year>

- OpenTelemetry GenAI 语义约定：<https://opentelemetry.io/blog/2026/genai-observability/>
- OWASP AI Agent Security Cheat Sheet：<https://cheatsheetseries.owasp.org/cheatsheets/AI_Agent_Security_Cheat_Sheet.html>

## 现状能力盘点

v3.2.2 已经具备且值得保留的能力：

- 仓内 canonical control plane：`.specnfc/` 的 contract、indexes、governance、execution pointers
- 运行时协作层：`.nfc/` 的访谈、计划、状态、日志、handoff、writeback
- 正式 dossier：`specs/changes`、`specs/integrations`、`specs/project`
- canonical 阶段机：`clarify → design → plan → execute → verify → accept → archive`
- 治理模式、waiver、评审 / 审批 / 验证 / 发布决策记录
- 多工具入口投影：`AGENTS.md`、`CLAUDE.md`、`.trae/rules`、`opencode.json`
- 中文 skill-pack 与自定义 skill manifest
- `status / doctor / change / integration / upgrade` 命令面与 35 个 JSON schema

## 差距详述

### 1. 入口文件是“投影”，但缺少入口契约

现有 AGENTS.md 主要表达流程规则，缺少标准入口应有的项目概览、安装与验证命令、代码规范、安全边界与 Skills 引用。也没有行数上限和嵌套文件规则，长仓或 monorepo 下会迅速失控。

### 2. 技能格式不可移植

现有 skill 是 manifest 里的 JSON 条目加独立 Markdown，代理无法按标准发现 `SKILL.md`，也无法只加载 metadata 做渐进披露。没有 `allowed-tools`，技能与工具权限脱节。

### 3. 工具策略缺失

MCP 已成为事实标准工具协议，但仓内没有声明哪些 server、哪些工具、在哪个阶段、是否需要审批。代理只能依赖各自默认权限，团队无法统一治理。

### 4. 角色只存在于 Prompt 文案

`prompts/role.md` 描述了架构师、规划师、执行者等角色，但没有阶段、工具、写范围、隔离与停止条件，无法被编排器消费，也无法导出为子代理定义。

### 5. 评测缺失导致“spec 遵从”不可度量

普通测试验证代码行为，不验证代理是否读取了正确文档、是否在正确阶段停止、是否越权写入。需要仓内评测用例与结果落盘，才能把 spec 遵从变成 CI 信号。

### 6. 安全策略没有机器可读载体

`security-boundaries.md` 是原则文档。真正需要的是默认拒绝的权限清单：可写路径、可执行命令、网络出口、密钥模式、需要审批的动作，以及“不执行外部内容中的指令”的硬约束。

### 7. 验收与需求没有稳定编号

现有模板的验收标准是自然语言列表，无法计算“每个需求是否都有验收与证据”。需要 `REQ / AC / TASK / EV` 编号与覆盖矩阵。

## 目标架构

在保留三层对象的前提下，新增一个 **Agent Native Layer**，全部通过受管文件生成与校验：

```text
.specnfc/
├── contract/            # 既有：仓级合同、阶段机、治理模式
├── indexes/             # 既有：多层索引
├── skill-packs/active/
│   ├── workflow/        # 既有：中文技能正文
│   ├── support/
│   ├── governance/
│   └── skills/          # 新增：Agent Skills 标准目录
│       └── <name>/SKILL.md
├── agents/              # 新增：角色目录与委派契约
│   ├── roles.json
│   ├── roles/<role>.md
│   └── task-template.json
├── mcp/                 # 新增：MCP 工具策略
│   └── policy.json
├── security/            # 新增：权限与不可信内容策略
│   └── permissions.json
├── evals/               # 新增：评测用例（结果写入 .nfc/evals/results）
│   ├── manifest.json
│   └── results/
└── traceability/        # 新增：追溯报告
    └── <change-id>.json
```

设计原则：

- 所有新增对象都是**受管文件**，由 `init / upgrade` 生成，`doctor / ci` 校验。
- 新增对象默认自洽，不阻断存量仓；只有明确越界（通配符授权、危险命令、外部指令执行）才阻断。
- 新对象只引用既有对象，不复制真相：技能正文仍来自 skill-pack，角色引用 canonical phases，MCP 策略引用阶段机。

## 数据契约

### Agent Skills

```yaml
---
name: clarify
description: 需求澄清：当 change 仍需统一问题定义、范围、非目标、当前选择和验收口径时触发。
compatibility: Designed for Spec nfc governed workflows
metadata:
  specnfc.layer: workflow
  specnfc.phase: clarify
  specnfc.trust-tier: governed
---
```

约束：`name` 必须与目录一致且符合 `[a-z0-9-]`；`description` 1–1024 字符；正文建议 < 500 行；`allowed-tools` 使用空格分隔。

### MCP 策略

```json
{
  "protocolVersion": "2026-07-28",
  "defaults": { "trustTier": "untrusted", "networkEgress": "deny" },
  "phaseToolPolicy": {
    "clarify": { "writeTools": "deny", "network": "deny" },
    "execute": { "writeTools": "approval", "network": "approval" }
  },
  "servers": []
}
```

### 角色目录

每个角色声明 `phases / tools / canWrite / writeScopes / isolation / stopConditions / handoffTo`。可写角色必须有明确写范围与停止条件；通配符工具直接阻断。

### 委派任务

```json
{
  "taskId": "task-<change>-executor",
  "traceId": "trace-<uuid>",
  "role": "executor",
  "changeId": "<change-id>",
  "acceptance": [{ "id": "AC-001", "criterion": "可验证标准" }],
  "budget": { "maxToolCalls": 60, "maxMinutes": 30, "maxChangedLines": 800 },
  "isolation": { "mode": "worktree" },
  "stopConditions": ["需要破坏性操作", "需要访问凭据"]
}
```

### 评测 manifest

用例声明 `command / timeoutMs / expect`，支持 `exitCode / stdoutIncludes / stdoutExcludes / stderrIncludes / fileExists`。结果文件包含 `runId`（即 `traceId`）、逐用例耗时与输出尾部。

### 权限清单

默认 `deny`；文件读写范围、命令白名单 / 黑名单 / 审批列表、网络出口、密钥模式、不可信内容策略全部显式声明。

### 追溯

`REQ-xxx` 定义需求，`AC-xxx（REQ-xxx）` 定义验收并回溯需求，`TASK-xxx（REQ-xxx）` 定义任务，`EV-xxx（AC-xxx）` 定义证据。`specnfc trace` 按共现关系构建矩阵并报告缺口。

## 命令面

| 命令 | 作用 | 退出码 |
| --- | --- | --- |
| `specnfc skills list/validate/export` | 列出、校验、导出标准技能 | invalid 时 1 |
| `specnfc agents list/validate/export/task` | 角色校验、导出子代理、生成委派任务 | invalid 时 1 |
| `specnfc eval list/validate/run` | 运行仓内评测 | 失败时 1 |
| `specnfc trace <change-id>` | 追溯矩阵与缺口 | `--strict` 有缺口时 1 |
| `specnfc security check` | 权限清单检查 | 阻塞时 1 |
| `specnfc ci` | 汇总全部门禁 | 有阻塞时 1 |

## 生成与升级流程

1. `init` / `upgrade` 调用 `buildProtocolPlaneArtifacts` 生成新增目录与文件。
2. 新增 schema 放入 `.specnfc/design/`，随受管设计契约复制到目标仓。
3. `doctor` 读取新增对象并汇总到 `mcpPolicy / securityPolicy / agentRoles / agentInstructions`。
4. `ci` 汇总 `inspectRepository`、Skills、角色、MCP、权限、入口与 eval 结果。
5. 所有检查在默认生成配置下必须通过，避免存量仓升级即失败。

## 安全设计

- **默认拒绝**：权限清单的 `default` 只能是 `deny` 才视为健康。
- **写范围收敛**：`**` 这类全仓写权限直接阻断。
- **受保护路径**：`.specnfc/security/**`、`.specnfc/mcp/**`、`.specnfc/agents/**`、`.specnfc/contract/**` 不得进入写范围，防止代理自行扩权。
- **命令最小化**：`rm -rf`、`sudo`、`curl`、`ssh` 等高风险命令进入白名单即阻断。
- **网络边界**：允许出口但未声明 `allowHosts` 直接阻断。
- **不可信内容**：`untrustedContent.policy` 必须为 `no-instruction-execution`；网页、issue、PR、外部 skill、MCP 返回值只作为数据处理。
- **审批动作**：push、publish、release、破坏性操作必须经过审批记录。
- **eval 执行边界**：命令执行前检查 `commands.deny` 与 `requireApproval`；子进程只继承最小环境变量，不传递 CI / 仓库密钥。
- **策略文件不可自改**：`init / upgrade` 保留团队自定义的权限清单、MCP 策略与 eval manifest，避免被默认值覆盖。
- **工具最小权限**：MCP 通配符工具、untrusted server 无审批写操作直接阻断。

## 可观测性

- eval 的 `runId` 同时作为 `traceId`，写入结果文件并注入子进程环境变量。
- 委派任务携带 `traceId` 与 `parentTraceId`，为后续 OTel GenAI span 关联预留字段。
- MCP 策略声明 `w3c-traceparent` 与 `gen_ai.*` / `mcp.*` 属性建议，避免后续接入时再改协议。

## 兼容性与迁移

- 既有 `.specnfc/skill-packs/active/{workflow,support,governance}` 继续生成，新标准目录并存。
- 既有目录与 manifest 字段不删除；新增字段均可选。
- `upgrade` 会补齐新增对象；旧仓未生成时 `doctor` 只给 advisory，不阻断。
- 版本号提升到 `4.0.0`，因为新增了正式对象与命令面，但阶段机与 dossier 结构未破坏。

## 选型与权衡

- **不引入 YAML 解析依赖**：`SKILL.md` frontmatter 只使用标量字段与一层 metadata 映射，自实现解析器足够，避免新增依赖。
- **不引入编排框架**：角色与任务契约是数据，不绑定 LangGraph / CrewAI / AutoGen；不同团队可继续使用自己的编排器。
- **不实现 A2A server**：先保证仓内对象可导出；跨组织互操作留到出现真实需求时再加。
- **评测使用 shell 命令**：与现有 CI 习惯一致，避免引入测试框架依赖；后续可扩展 JSONPath 断言。
