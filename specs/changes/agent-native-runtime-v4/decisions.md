# 关键决策

## D-001：采用渐进式 Agent 原生层，而不是重写框架

- 背景：现有 3.x 的阶段机、dossier 与治理记录已被团队使用。
- 决策：保留三层对象与命令面，在 `.specnfc/` 内新增 Agent 原生对象。
- 理由：可在不破坏存量仓的前提下交付可执行能力；每个对象可独立回滚。
- 影响：新增受管产物与检查，但默认不阻断存量仓。

## D-002：以 `SKILL.md` 作为技能分发格式，保留旧目录

- 背景：Agent Skills 已成为开放标准，旧 skill-pack 仍有大量中文正文。
- 决策：从旧 skill-pack 生成 `.specnfc/skill-packs/active/skills/<name>/SKILL.md`，旧目录继续存在。
- 理由：避免一次性迁移 26 个技能正文；标准目录可被任意代理加载。
- 影响：同一技能存在两份投影，真相仍在 skill-pack 源。

## D-003：MCP 默认不信任、默认拒绝网络

- 背景：MCP server 质量与来源差异大，prompt injection 风险高。
- 决策：`trustTier` 默认 `untrusted`，`networkEgress` 默认 `deny`；远程 server 要求授权声明。
- 理由：假设注入会成功，先限制爆炸半径。
- 影响：团队接入真实 server 时必须显式提升信任级别并声明工具。

## D-004：角色与委派是数据，不绑定编排框架

- 背景：团队使用的代理与编排器不同（Claude Code、Codex、自研）。
- 决策：角色目录与任务契约使用中立 JSON / Markdown；导出时再适配具体工具。
- 理由：避免锁定单一供应商；契约可被任何编排器消费。
- 影响：需维护工具名映射，但不影响协议层。

## D-005：评测使用 shell 用例，进入 CI

- 背景：spec 遵从度需要可度量，但引入评测框架会增加依赖。
- 决策：`.specnfc/evals/manifest.json` 中的命令直接通过 `/bin/sh` 执行，断言 exitCode / stdout / 文件存在。
- 理由：与现有 CI 习惯一致，零新增依赖；后续可扩展结构化断言。
- 影响：用例需要团队自己维护；默认 smoke 只覆盖协议骨架。

## D-006：追溯依赖显式编号，而不是推断语义

- 背景：自然语言验收标准无法可靠计算覆盖。
- 决策：使用 `REQ / AC / TASK / EV` 稳定编号，按共现关系建立矩阵。
- 理由：显式编号比语义推断更可解释、更可审计。
- 影响：change 模板增加编号 section；未使用编号的旧 change 报告 `not-adopted`，不阻断。
