# 需求与方案

## 变更标识

- ID：`agent-native-runtime-v4`
- 标题：Spec nfc v4.0 Agent 原生运行时升级
- 类型：`design-system`

## 问题定义

`Spec nfc` 3.x 已经解决了“需求、设计、计划、验收必须落成仓内文档”的问题，但 2025–2026 年的团队 agent 工程发生了三个结构性变化：

1. **指令入口标准化**：`AGENTS.md` 成为跨工具事实标准（60k+ 公开仓，Linux Foundation Agentic AI Foundation 托管），并约定嵌套文件“就近优先”。
2. **能力封装标准化**：Agent Skills 成为开放标准，`SKILL.md` 通过 frontmatter 与渐进披露控制上下文成本。
3. **工具与协作协议标准化**：MCP `2026-07-28` 转向 stateless 核心与扩展框架；A2A v1.0 定义跨组织 agent 互操作；多代理编排普遍采用 orchestrator-worker + 隔离 worktree + 人工审批点。

现有 spec 仍主要以“给人看的文档合同”为中心，缺少机器可执行的 agent 运行时对象：技能不是 `SKILL.md` 格式、没有 MCP 工具策略、没有角色与委派契约、没有评测门禁、没有权限清单、没有需求到证据的追溯。结果是：文档齐全时，代理行为仍不可约束；代理行为正确时，也无法证明它遵守了 spec。

## 目标

1. 让 `specnfc init` 生成的仓可以直接被任意遵循 AGENTS.md / Agent Skills 的编码代理消费。
2. 让技能、工具、角色、权限、评测都成为仓内可校验的正式对象，而不是口头约定。
3. 让需求、验收、任务、证据形成可计算的追溯矩阵，并把缺口变成 CI 可阻断信号。
4. 保持 3.x 的阶段机、dossier、治理记录与升级路径，不推倒重来。

## 非目标

- 不在本版本内实现 A2A server 或跨组织 agent 网络运行时。
- 不绑定任何单一模型供应商或 IDE；所有新增对象保持工具中立。
- 不引入需要常驻服务的控制面；所有能力必须能在本地 CLI 与 CI 中运行。
- 不自动执行高风险的发布、推送与凭据访问动作。

## 范围

- 本次包含：Agent Skills、MCP 策略、角色与委派、评测、权限清单、AGENTS.md 标准检查、追溯矩阵、统一 CI 门禁。
- 本次不包含：托管式团队控制面、模型路由、向量记忆服务、A2A 网关。

## 方案备选

### 方案 A：继续扩充文档模板

- 做法：只增加更多规范章节与检查清单。
- 优点：改动最小，不破坏现有结构。
- 风险：仍然无法约束代理行为，无法机器验证，无法进入 CI。

### 方案 B：推倒重写为 agent 框架

- 做法：引入新的运行时与编排服务，替换现有 CLI。
- 优点：可以一次性对齐所有新范式。
- 风险：破坏 3.x 的仓内资产、迁移成本高、与团队现有工具链冲突。

### 方案 C：在现有控制面上增加 Agent 原生层

- 做法：保留 `.specnfc/`、`.nfc/`、`specs/` 与阶段机，新增技能、工具、角色、权限、评测、追溯对象，并接入 `doctor / ci`。
- 优点：增量可交付；既有 dossier 与治理记录继续有效；新增对象默认可选、可校验、可升级。
- 风险：对象数量增加，需要严格控制默认值与阻断边界。

## 当前选择

- 当前选择：方案 C，渐进式增加 Agent 原生层。
- 选择理由：与仓库既有分层和升级机制一致；每个新增能力都能独立交付、独立测试、独立回滚；不要求团队更换现有代理。
- 不选其他方案的原因：方案 A 无法解决可执行性；方案 B 违反“在已能工作的产品上增加能力”的原则。

## 需求编号

- REQ-001：仓内技能必须符合 Agent Skills `SKILL.md` 标准，可校验、可导出、支持渐进披露。
- REQ-002：仓内必须声明 MCP 工具策略，按 canonical phase 约束读、写与网络出口。
- REQ-003：仓内必须声明多代理角色，包含阶段、工具、写范围、隔离方式和停止条件。
- REQ-004：代理委派必须使用结构化任务契约，携带 traceId、预算与验收标准。
- REQ-005：仓内必须提供可运行的评测用例与结果落盘，并能作为 CI 门禁。
- REQ-006：仓内必须提供默认拒绝的权限清单与不可信内容策略。
- REQ-007：`AGENTS.md` 必须符合标准入口结构，并受规模与引用检查约束。
- REQ-008：需求、验收、任务、证据必须形成可计算的追溯矩阵与缺口报告。

## 风险与验收口径

- 关键风险：新增检查过严导致存量仓无法通过；默认策略过于宽松导致门禁失效。
- 缓解方式：所有新检查默认对存量仓不阻断，只有明确越界配置或结构损坏才阻断；默认生成对象必须自洽。
- 验收口径：`npm test` 全绿；新仓 `specnfc ci` 通过；越界配置可被 `security / ci / doctor` 明确阻断；追溯矩阵可识别缺口。
